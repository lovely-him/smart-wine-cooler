# 代码结构

> 这份文档规定**东西该放在哪、谁能 import 谁**。想知道现在代码在哪，看 [代码地图](代码地图)。
> 违反本页的地方就是要改的地方，不是「先这样」。
>
> **本页是目标设计，不是现状**——只有 §9 是实测到的差距。§2 的目录骨架与 §3 的依赖方向已定（服务层粒度：一个模块一个 service）；改本页要同步改代码地图。

---

## 1. 唯一判据

> **改一个功能，影响面只应该沿着一个方向扩散。**

具体说：加一个接口不该动业务逻辑；换一个模型不该动界面；改一条规则不该动数据库。

做不到的原因几乎只有一个：**依赖方向乱了**——上层细节被下层业务直接摸着用。

---

## 2. 目标目录

```
server/
  kernel/        纯对象与纯规则：数据对象、位置次序、差异计算、业务错误
  platform/      基础设施：SQLite 与仓储、事件总线、日志缓冲、回收、系统探测、网络、
                 引导信息与采集参数（`bootstrap` / `layers` / `settings_def`）
  vision/        采集与识别：设备枚举、抓帧、静止判定、镜头矫正与标定、检测、分类、参考库
  settings/      配置项读写、设备口令、维护动作（重启/导出/灯）
  catalog/       类别与字段、参考图管理、AI 补全、未识别分组
  observe/       触发调度、一次观察的编排
  checkpoint/    差异、提交、历史查询与删除
  api/           HTTP 边界：路由、请求/响应形状、SSE、预览图
  app.py main.py 组合根与入口
```

**配置出厂值放 `platform`（最容易被误放进 `kernel`）**：`cam.cameras` / `cam.layers` 的默认值里有设备路径与尺寸，还吃 `CAMERA_*` 环境变量——它是「本机长什么样」，不是纯规则。放进 `kernel` 就会让内核读环境变量，直接破 §3 第 3 条。

**每个模块 = 一个业务词。** 判断法：这个目录名能不能用一句产品里的话说清（「观察」「类别」「配置」能；「models」「utils」不能）。

**服务层粒度：一个模块一个 service。** 不按用例拆（`StartObserve` / `GetSnapshot` 各一个类）——这个规模下那只是把函数名变长，属于过度抽象。一个 service 里放这个模块的若干个方法就好。

## 3. 依赖只能向内

| 层 | 模块 | 允许 import |
| :---: | --- | --- |
| 0 | `kernel` | 标准库、pydantic。**不许 import 本项目任何其他模块** |
| 1 | `platform` | `kernel` |
| 2 | `vision` | `kernel`、`platform` |
| 3 | `settings`、`catalog` | `kernel`、`platform`、`vision` |
| 4 | `observe`、`checkpoint` | 层 0–3 全部 |
| 5 | `api` | 层 0–4，但**只调各模块的 service，不许 import `platform/db`** |

**数字大的可以 import 数字小的，反过来禁止。** 同层之间允许互相调用，但不许形成环。这条由 `tools/check/lib/layers.py` 守着（`check.sh quick` 会跑）。

三条最容易破的，单独写死：

1. **`api` 不碰数据库。** 接口只做三件事：解析请求 → 调一个 service → 序列化结果。它一旦能直接查库，业务就会漏进接口层，将来加个命令行或定时任务只能复制一遍。
2. **业务不 new 基础设施。** 需要数据库、模型、摄像头，一律从构造函数收进来，不在函数体里 `Database(...)`。
3. **`kernel` 里没有 IO。** 不读文件、不连库、不开摄像头、不看当前时间（时间从参数进）。这样规则能用纯函数测。

## 4. 组合根只有一个

**只有 `app.py` 允许 `new` 具体实现**，并把它们塞给各模块：

```python
db = Database(...)
vision = VisionService(db=db, cameras=load_camera, ...)
observe = ObserveService(db=db, vision=vision, config=settings, events=bus)
api = build_router(observe=observe, checkpoint=checkpoint, ...)
```

前后端同一套思路：前端把这条线写在 `index.tsx`（`createWineCoolerUseCases(createHttpWineCoolerPort(""))`），后端写在 `app.py`。

### 不许把整个系统当参数传

```python
# ❌ 下游不知道自己要什么，只知道「给我整个系统」
run_scan(runtime)
commit(runtime, body)

# ✅ 说清需要两样东西
run_scan(db=db, vision=vision, config=config)
```

判据：**看一个函数的签名，能不能知道它依赖什么。** 不能，就是传了容器。

## 5. 端口（业务需要的能力，由业务自己声明）

不是每个依赖都要造接口。**只在「实现会换」或「测试要替换」时才定端口**，两条都占不到就别抽象（CLAUDE.md：不做过度抽象）。

| 端口 | 为什么值得 |
| --- | --- |
| 采集源 | 板上是 V4L2，宿主机是图片目录，测试是假帧序列 |
| 检测器 / 特征提取 | 板端 rknn、宿主机 onnx、测试可给固定结果 |
| 摄像头枚举 / 门磁 / 灯 | 有硬件与模拟两种，宿主机要能跑完整链路 |
| 事件通道 | 真实是 SSE，测试里不需要真连接 |

端口写在**使用它的模块里**，实现放 `platform` 或 `vision` 的适配文件里。

## 6. 单一真相源

| 东西 | 真相源 | 别人怎么用 |
| --- | --- | --- |
| 接口数据形状 | `kernel/objects.py` | 导出 openapi → 前端生成类型，**前端不手写镜像** |
| 写操作的请求形状 | `api/schemas.py` | 只在 HTTP 边界用，不进业务层 |
| 层内位置次序 | `kernel/ordering.py` | 推理、提交、位置历史三处**共用一份** |
| 配置项与出厂值 | `platform/settings_def.py` | wiki `SET §4` 的编号必须与它逐条一致（`check.sh docs` 守着） |
| 采集源结构 | `platform/layers.py` | 采集与配置两处**共用一份**解析，不各写一套 |
| 环节先后顺序 | 各模块 service | 顺序写一次，不允许多处各写一套 |

## 7. 文件与命名

- **一个文件一件事**：文件名读出来就该知道里面是什么。出现 `utils.py`、`helpers.py`、`common.py`，说明还没想清楚归属
- **模块对外只暴露 service**：`__init__.py` 只做导出，不放逻辑
- **函数优先级**：纯函数 > 方法 > 全局状态。能用纯函数写清楚的规则，不要挂到类上
- **注释**：只写代码看不出来的坑（CLAUDE.md 1.2）。「这个函数干什么」靠文件名，不靠注释

---

## 8. 边界必须可替换

| 边界 | 做法 | 为什么 |
| --- | --- | --- |
| 时间 | 需要「现在几点」的地方收一个 `now` 参数 | 否则去抖、保留策略没法测 |
| 随机 | 同上 | — |
| 文件/设备 | 端口 | 宿主机没有摄像头也要能跑完整链路 |
| 模型 | 端口 | 同一个流程要能在两种后端上跑 |

## 9. 这些约束怎么守着

不靠人眼，靠五道闸，`./tools/check/check.sh all` 一次跑完：

| 闸 | 守什么 | 在哪 |
| --- | --- | --- |
| 语法与导入 | 每个模块都 import 得进来——循环依赖、写错的路径当场暴露 | `check.sh quick` |
| 分层依赖 | 本页 §3 的方向：反向依赖与 `api` 直接碰库都会报错，不是靠自觉 | `check.sh quick`（`lib/layers.py`） |
| 文档编号与引用 | wiki `SET §4` 的编号与 `platform/settings_def.py` 逐条一致、跨页引用不悬空 | `check.sh docs` |
| 单元测试 | 规则层与流程层的行为 | `check.sh unit` |
| 接口快照 | 24 个用例的状态码与响应体与 `tools/baseline/golden.json` 逐条一致 | `check.sh baseline` |

**接口快照能管的与管不了的**：它只回答「返回和上次记的一样吗」。变了不等于坏了——是不是想要的变化，看 diff 由人定。有意改接口时跑 `tools/baseline/run.sh update` 刷新基线，并把改动写进提交信息。

**想让它自动跑**：`git config core.hooksPath .githooks` 一次，之后提交前自动跑全量（hook 就在库里，改规则不用重装）。三个边界要知道：查的是**工作区**不是暂存区；`git commit --no-verify` 能绕过；每次提交多花十几秒。

**闸之外靠人守的两件事**：

1. **接口形状变了**，要跑 `python3 -m server.openapi` 重新生成前端类型，别手改 `api-types.ts`。
2. **涉及硬件时序的改动**（门磁、灯、采集），单测用假实现只能保逻辑，必须上板跑一次真实观察。

**批量改代码时**：改 import、改包名的脚本**只扫指定目录**，别对仓库根 `rglob('*.py')`——`.venv` 会被一起改坏，且报错现场与真凶无关。

---

## 10. 什么时候可以破例

只有两种：

1. **一次性脚本**（`tools/`、`-m server.openapi` 这种）不必遵守分层，但**不许被业务代码 import**
2. **性能热点**里允许绕过封装直接取数据，前提是旁边写清「为什么这里不能走正常路径」

破例也只能破一次：同样的破例出现第二次，说明规范该改，而不是代码该继续绕。
